## 补齐增值保障计算链路（用户指出只干了一半）

- 用户指出：detail 原有的 `insuranceDetail()` / `insuranceFee()` 两个 computed
  被删掉后没有等价实现挪到 confirm，会断功能。核实确实有两个隐患：
  1. 之前用 `syncInsurance` 手动写 `item.insuranceFee` 快照替代自动派生，
     一旦漏调用 / 详情接口失败，明细与金额不同步（把 computed 降级成手动同步）；
  2. `normalizeInsuranceDetail` 的 `.filter(d => d.code)` 会把购物车老数据
     （只有 name/fee、无 code）整条丢掉，已买保障进确认页凭空消失且费用归零。
- 修复：在 confirm 新增按件派生的 `itemInsuranceDetail(item)` /
  `itemInsuranceFee(item)`（多商品场景 computed 不能带参数，故用方法，语义等价），
  并把 `insuranceTotal` / `itemSubTotal` / `itemServiceText` / `createOrder.items`
  全部改为走派生值，快照字段降级为兼容用途。
- 配套修复：无 code 时用 name 作标识；loadSkuInfo 把快照按 code 或 name 映射到
  当前 options；`insuranceTouched` 标记区分「用户没动过 → 保住快照」与
  「用户主动取消全选 → 必须归零」；options 未加载 / 接口失败时回退快照。
- 验证：用 vm 加载真实 SFC script 跑 18 组场景（老数据、加载中、映射、
  加选、全取消、code 对不上、各金额 computed），18/18 通过；两个 SFC 解析通过。
- 设计口径：detail 不再提供勾选，加购与立即购买都传空保障，
  confirm 是唯一勾选入口；购物车/立即购买两条链路都在 confirm 现选现算。
